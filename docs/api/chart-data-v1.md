# Chart data API, v1 (notes for the alerenzi plugin team)

astro-report computes natal charts, transit windows, synastry with a midpoint
composite and solar returns on request, for one client: the alerenzi consultation
plugin. It stores nothing about the people it is asked about. The plugin keeps the
responses it receives; this service keeps no copy.

The contract behind this page is `_bmad-output/specs/spec-astro-report/SPEC.md`
and the Epic 11 stories. Every example below is **generated by the code and
checked by `tests/test_api_doc_examples.py`**: if a response changes, the test
fails until the example is regenerated. Do not edit an example by hand
(`REGENERATE_API_DOC=1 uv run pytest tests/test_api_doc_examples.py` rewrites them).

## Endpoints

All paths are under `/api/v1`. All bodies are JSON (UTF-8). Every request carries
`Authorization: Bearer <token>`; the token is issued to the plugin by Francesco and
is the only credential accepted here (session cookies are not).

| Method | Path | Purpose |
|---|---|---|
| POST | `/places/resolve` | Place text to candidates, each with an IANA zone |
| POST | `/charts/natal` | One natal chart |
| POST | `/charts/transits` | Transit events over a window of up to 13 months |
| POST | `/charts/synastry` | Two natal charts, inter-aspects, house overlays, midpoint composite |
| POST | `/charts/solar-return` | The solar return of a year, at the birthplace or relocated |
| GET | `/vocabulary/it` | Italian names for every id the API uses, plus the Gate words |

Requests are synchronous: the response is the result. A 12-month transit window is
the slowest call; see the latency record in
`docs/release-validation/latency.md` for the status of its measurement.

## Shapes

### Subject and place

A subject is `{label, birth_date, birth_time, time_known, place}`:

- `label`: free text up to 200 characters, kept by you, never interpreted.
- `birth_date`: `YYYY-MM-DD`, the **local civil** date.
- `birth_time`: `HH:MM` or `HH:MM:SS`, the **local civil** time; required when
  `time_known` is true, ignored (send `null`) when it is false.
- `time_known`: a JSON boolean.
- `place`: exactly one candidate from `/places/resolve`, returned unchanged:
  `{latitude, longitude, iana_zone, display_name}`. Coordinates are decimal strings
  with 4 decimal places.

`/places/resolve` takes `{"query": "<text>"}` (1 to 200 characters) and returns
`{"candidates": [...]}`, every match listed in the geocoder's order. Show the
candidates to your operator and send the chosen one as `place`. No match at all is
`place_unresolved`. The only thing this endpoint writes is the place cache.

Angles and longitudes are decimal strings with 4 places in `[0, 360)`. Instants are
UTC ISO-8601 with a trailing `Z`. Bodies, signs, aspects and directions use fixed ids
(`sun`, `moon`, ..., `pluto`, `true_node`, `south_node`, `ascendant`, `midheaven`;
`aries` ... `pisces`; `conjunction`, `sextile`, `square`, `trine`, `opposition`;
`direct`, `retrograde`). The Italian names come only from `/vocabulary/it`.

### Responses

Every chart response carries a `meta` block (API version, ComputationConfig
version and hash, orbs, house system, SHA-256 of the ephemeris manifest, zodiac
`tropical`). Store it next to the frozen result: it says exactly which computation
produced it. Vocabulary and places responses have no `meta`.

| Endpoint | Top-level keys |
|---|---|
| natal | `chart` (`planets`, `houses`, `ascendant`, `midheaven`, `aspects`, `house_rulers`), `subject`, `meta` |
| transits | `aspects`, `ingresses`, `lunations`, `standing_retrogrades`, `stations`, `window_utc`, `subject`, `meta` |
| synastry | `natal_a`, `natal_b`, `inter_aspects`, `overlays` (`a_in_b`, `b_in_a`), `composite`, `subjects`, `meta` |
| solar return | `chart`, `comparison`, `return_instant_utc`, `location`, `subject`, `meta` |
| vocabulary | `vocabulary_version`, `content_hash`, `gate`, `bodies`, `signs`, `aspects`, `directions` |

`subject` echoes the label, the local date and time, the place, the `utc_offset` in
force then, and the UTC instants the chart was computed at.

## Error codes

Every failure is `{"code", "message", "field"}`; `message` is Italian and fit to show
an operator, `field` is the JSON path concerned (or `null`). Branch on `code`.

| Code | Status | When |
|---|---|---|
| `invalid_request` | 422 | Malformed JSON shape, a bad date or time, an empty or inverted window, a DST gap or fold (`field: "subject.birth_time"`) |
| `birth_time_required` | 422 | A calculation that needs the birth time was asked with `time_known: false` (the solar return) |
| `place_unresolved` | 422 | `/places/resolve` found nothing |
| `window_too_long` | 422 | A transit window beyond 13 calendar months |
| `ephemeris_out_of_range` | 422 | A date or year outside 1801 to 2399, or a return beyond the last covered year |
| `unauthorized` | 401 | Missing, malformed or wrong bearer token (always JSON, never a redirect) |
| `internal_error` | 500 | Anything else; the body never carries internal detail |

## Determinism

The same request, ComputationConfig and ephemeris give **byte-identical** bodies:
canonical JSON (sorted keys, no whitespace), no timestamp, no request id. You can
hash a response to detect change. A different `meta.computation.content_hash` or
`meta.ephemeris.manifest_sha256` is the signal that an old result was computed
differently.

## Birth time and daylight saving

Send the local civil date and time; the service converts them to UTC with the
historical offset for that place and instant. A local time that never happened (the
spring-forward gap) or happened twice (the autumn fold) is `invalid_request` with
`field: "subject.birth_time"` (`subject_a.birth_time` / `subject_b.birth_time` in
synastry). It is never guessed: ask your operator which instant they mean and send
an unambiguous time.

## Unknown birth time

`time_known: false` is supported by the chart endpoints (not by reports). The chart
is cast for local noon and has **no angles, houses or house-dependent output**
(`ascendant`, `midheaven`, `houses` and `house_rulers` are `null`, every planet's
`house` is `null`). Each body carries `range` (`from`, `to`) across the local day;
the Moon moves about 14 degrees, so its sign can be uncertain (`sign_uncertain`).
Transits for an unknown time omit the angle and Moon targets and all house output.

In synastry each person's overlays and the composite's angles, houses and
house-dependent items are `null` when a needed birth time is missing; the example
with one unknown time shows exactly which. The composite needs both times for its
angles and houses. The solar return needs the natal Sun to the arc-minute, so
`time_known: false` there is `birth_time_required`.

## Windows and year limits

A transit window is `{start_date, end_date}`, local dates in the subject place's zone,
half-open (`end_date` is not included), converted to one UTC interval. The longest
window is 13 calendar months from `start_date`; one day more is `window_too_long`.
The vendored ephemeris covers the years 1801 to 2399: a birth date, window date or
solar-return year outside it is `ephemeris_out_of_range`. A solar return `year` must
not precede the birth year.

## Version policy

The prefix is the version. Within `/api/v1` only additive changes happen (new fields,
new endpoints): ignore fields you do not know. A breaking change is a new prefix,
`/api/v2`, announced before `/api/v1` is touched. `vocabulary_version` and
`content_hash` change when a word list changes; cache the vocabulary against them.

## Network setup

The plugin reaches astro-report from the WordPress container over the VPS's shared
Docker network, never over the public internet:

1. Francesco attaches the astro-report container and the WordPress container to one
   Docker network in Coolify (the exact network name and the service hostname are
   his to supply; they are not recorded here).
2. The plugin calls `http://<astro-report-service-name>:<port>/api/v1/...` with the
   bearer token.

**Public HTTPS fallback.** If the shared network is not possible, the same API is
reachable at the application's public HTTPS hostname. The bearer token is then the
only protection, so use HTTPS only, never log the `Authorization` header, and tell
Francesco so the token can be rotated if it ever leaks.
