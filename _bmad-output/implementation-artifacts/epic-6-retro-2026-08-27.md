`deferred-work.md:517-519,541-543`. Disposition: **defer** — extract when one of those routes is
next legitimately in scope; process lesson: specs that clone a route should schedule the helper
extraction as an explicit companion item, not leave it implicit. Source: `report_runs.py:323-350`
vs `423-450`; `deferred-work.md:517-543`.

**D2 (defer, minor) — "the latest ExportRecord for a run" is queried two ways, both run on one POST.**

### Diff-scope review (adversarial / edge-case / verification-gap)

The three code lenses were run **inline** over the epic diff (`shell/` + `migrations/` + `tests/`,
~733 source lines added, ~2600 test lines), scope-narrowed and recorded here: `bmad-review` was not
spawned as a separate multi-agent pass to keep this background run bounded, and each Epic 6 story
already went through its own Blind Hunter review loop whose findings are captured in
`deferred-work.md`. This pass folds the cross-cutting ones forward and verifies each against current
code before keeping it.

**F1 (fix-now — potentially release-blocking) — the migration chain cannot reach a fresh Postgres
database.** The Alembic revision id `0014_bound_client_and_chart_string_columns` is **42 characters**;
Alembic's default `alembic_version.version_num` column is `VARCHAR(32)`. `migrations/env.py` sets no
`version_table` / column-width override, and no migration alters `alembic_version`. So
`alembic upgrade head` from any state at or before `0013_gate_result` fails with
`StringDataRightTruncation` when it tries to stamp `0014` — and **all four of Epic 6's migrations
(`0015`–`0018`) chain off `0014`**, so the entire Epic 6 schema delta (`export_record`,
`export_record.disposition`/`elapsed_seconds`, `report_run.natal_chart_id`, `backup_record`) is
unreachable behind it. The migration test suite never catches this: `tests/test_migration_chain.py`
only runs `alembic upgrade head --sql` (offline SQL emission, nothing executes it) against a fake
`postgresql://db.example.eu` URL, and the adapter tests run on SQLite, which does not enforce
`VARCHAR(n)` length. `deferred-work.md:22-24` records that this was *"confirmed independently twice …
against a real throwaway Postgres container"* and that *"every migration from `0014` onward,
including this story's own `0017`, has never actually been exercised end-to-end from a clean
database."* Consequences: (a) if the deployed Render database's `alembic_version.version_num` is
still stock `VARCHAR(32)`, every deploy since baseline `6f79831` has been failing at the
`alembic upgrade head` entrypoint step and Epic 6's features are not actually live; (b) Story 8.5
(restore into a fresh DB) is blocked before it starts, defeating Story 6.5/6.6's whole purpose.
This is *pre-existing* — introduced by deferred-work-41's `0014`, which is Epic 6's baseline commit,
not one of its own — but Epic 6 stacks its entire schema on top of it. Same failure *class* as G1:
the test database is more permissive than production, so a production-only failure ships green.
Disposition: **fix-now**. Source: `migrations/versions/0014_bound_client_and_chart_string_columns.py:34`;
`migrations/env.py` (no override); `tests/test_migration_chain.py:104-138`; `deferred-work.md:22-24`.

**F2 (defer) — `list_client_reports` has no same-month tiebreak, exactly where the epic's own
superseded-chart case creates same-month siblings.** `shell/http/routes/clients.py`
`list_client_reports` orders by `ReportRun.month.desc()` alone (`month` is zero-padded `"%Y-%m"`, so
that ordering is chronologically correct). But nothing stops two passed Reports for the same
`(client_id, month)` — `start_report_run` has no uniqueness check — and Story 6.4's headline feature
is marking an entry whose chart was *since superseded*, i.e. a month regenerated after a correction:
precisely the case that yields two same-month entries, now rendered in undefined relative order with
no way to tell them apart. Echoes the still-open `epic-4-retro-item-28` (add a `created_at` tiebreak
to `most_recent_prior_report_theme` for same-month `ReportRun`s) — same root cause, new surface.
Already `deferred-work.md:14-16`. Disposition: **defer**; bundle with `epic-4-retro-item-28`.
Source: `shell/http/routes/clients.py` (`list_client_reports` query); `deferred-work.md:14-16`.

**F3 (defer) — GET routes with durable side effects; one corrupts the 6.6 staleness signal.**
`GET /report-runs/{run_id}/export/pdf` writes an `ExportRecord` (and may advance `run.stage`) on
every call; `GET /backup` runs `store_backup_record(session); session.commit()` on every call. A
browser prefetch, crawler, proxy, or accidental retry silently inflates the export audit trail —
and, worse, records a `backup_record` row for a "backup" that was never a deliberate operator
action, which immediately clears the Story 6.6 "backup out of date" warning. Both are consistent
with the pre-existing `poll_report_run` GET-with-side-effects precedent in the same module, so
neither is unique to this epic — but the `/backup` case degrades the honesty of the very signal
Story 6.6 exists to provide. Already `deferred-work.md:530-531,582-583`. Disposition: **defer**; at
minimum make the `backup_record` write resilient to non-deliberate hits, or move recording to a
POST/confirmation step. Source: `report_runs.py:462-469`; `backup.py:99-103`;
`deferred-work.md:582-583`.

**F4 (defer, minor) — `record_send_disposition`'s boolean return is dead information at its only
call site.** The function returns `bool` specifically to distinguish "no `ExportRecord` for this
run" from "latest already has a disposition" — but `record_export_disposition` does its own
`_latest_export_record(...) is None` existence check *first* and then ignores the return value
entirely, so the distinction the bool encodes is never consumed. A sharp edge for any future second
caller (a script, a background job) that trusts the bool alone. Already `deferred-work.md:562-563,570-571`.
Disposition: **defer**. Source: `report_runs.py:501-509`; `export_record.py:122-162`.

**F5 (accept — adequately tested) — the WeasyPrint / PDF path has real executed coverage.**
`tests/test_http_report_runs.py::test_the_first_export_returns_a_pdf_and_advances_the_run_to_exported`
and two siblings run the real `html_to_pdf` and assert `response.content.startswith(b"%PDF")`;
`test_the_exported_html_contains_only_the_eight_sections_and_the_clients_name` monkeypatches
`html_to_pdf` to capture and assert on the HTML string (a real PDF's content stream is not
plain-text-searchable). Boundary tests cover 401 / unknown run / gate-not-passed / terminally-failed
/ repeat-export-stage-unchanged. No finding. Source: `tests/test_http_report_runs.py:1453-1533`.

**F6 (defer — cosmetic but client-facing) — the exported PDF shows raw `snake_case` section keys and
ships with no CSS.** `report_export.html` renders headings as `energia_generale`,
`giorni_di_attenzione`, `consiglio_finale`, … — the internal keys — in a document meant to be handed
directly to a paying client, and with no page-break control, margins, or typography. Inherited
verbatim from `report.html`/`report_draft.html` (Stories 4.6/6.1), which the story's Boundaries
required reusing. Fixing it well needs a shared section-title map that also improves the on-screen
views. Already `deferred-work.md:534-539`. Disposition: **defer**. Source:
`shell/http/templates/report_export.html`; `deferred-work.md:534-539`.

**F7 (defer — ops / security) — `/backup` returns an unencrypted plaintext dump of every Client's
PII with no downstream handling guidance.** Names, birth dates/times, precise coordinates, all
Report prose. `Cache-Control: no-store` was added during story review, but nothing addresses
encryption at rest, secure storage, retention, or rotation once the file leaves the browser — an
operational decision, not a code change, but a real one given the export's sensitivity. Already
`deferred-work.md:578-579`. Disposition: **defer**; document operator handling before the route sees
regular use. Source: `backup.py:99-113`; `deferred-work.md:578-579`.

**F8 (verification gap) — no runtime behavior was exercised.** No reachable Postgres in this
environment (same as every prior epic retro — epic-2-retro-item-18, epic-3-retro-item-22). Not
checked in a browser: the Report view and its one-click Payload link, the "View Report" link from
the poll page, the PDF download and its content, the disposition one-click forms and their
set-once/replaced-by-text behavior, the Report History listing and superseded marking, the backup
download, and the staleness banner. All are covered by HTTP-level tests against SQLite; none has
been seen running against Postgres or in a browser. Recorded as **never checked**, not "checked and

**Consolidation note.** F1 and G1 are the same failure class, twice in one epic: the test database
(SQLite, offline `--sql`) is more permissive than production (Postgres) — SQLite ignores

6.4 already paid for this once (an FK-ordering bug that passed 1118 tests). Worth a standing
practice change: any migration or cascade change gets one test that runs against a real Postgres.
