### Diff-scope review (story-boundary interactions)

Three lenses (adversarial, edge-case-hunter, verification-gap) ran via `bmad-review` against the full epic-2 diff, scoped to interactions between stories that no single story's own review could see. Each agent was told not to re-report anything already in `deferred-work.md`'s `spec-2-*` entries, and each independently confirmed several seams the task asked about are actually handled correctly: 2.6's chart lookup already filters `superseded_at IS NULL` (fixed within 2.7's own commit, verified via `git diff a45f792 0703782`); Rulers/Domain Profiles (2.4/2.5) have zero call sites anywhere in `shell/`, so a "stale Ruler vs. current chart" bug is not yet reachable; and 2.8's cascade is genuinely tested against a Client with a real superseded row, not a vacuous fixture (`tests/test_client_store.py:227-261`, `tests/test_http_client_deletion.py:262-297`).

Two findings below were re-verified directly against current source (not just taken on the sub-agent's word), per this skill's rule that sub-agent findings are reports, not facts, until re-checked:

1. **The correction flow's own "PLACE_CACHE absorbs a repeat lookup" claim is false for any genuinely new place, and the test suite cannot catch this.** Verified by reading `shell/http/routes/clients.py:365-502` (`correct_client`) and `shell/http/app.py:61-71` (`get_session`) directly. `get_session`'s own docstring states plainly: "Closing the session without an explicit `commit()` rolls back any pending work, including a nested `PLACE_CACHE` write." `correct_client` calls `geocoder.resolve()` unconditionally at line 444 — on *both* the warning-showing request and the later confirming request — but only calls `session.commit()` once, at line 500, *after* the confirm gate. The warning-step request (line 481-487, `confirmed != "1"`) returns without ever committing, so a fresh-place resolution's `PLACE_CACHE` write-through is silently rolled back when that request's session closes. The confirming resubmission then re-resolves against a cache that was never actually written, hitting Nominatim live a second time — directly contradicting `correct_client`'s own docstring comment (line 376: "re-running resolution is cheap — `PLACE_CACHE` absorbs a repeat lookup"). Compounding this: `tests/test_http_client_correction.py` overrides `get_session` with a single, never-closed `Session` shared across every request in a test (confirmed by the verification-gap lens against the fixture at line 201-204), which does not reproduce production's per-request session lifecycle — so no test in the current suite is even structurally capable of catching this, and the verification-gap lens independently confirmed the real `Geocoder`/`PLACE_CACHE` chain is never exercised end-to-end through either the create or correct HTTP routes at all (every HTTP-layer test replaces `get_geocoder` with a fake).
2. **The chart-wheel verification tool can silently disagree with the chart it claims to be showing.** Verified by reading `shell/http/routes/chart.py:43-69` directly. `chart_wheel_view` renders aspects by recomputing them live via Kerykeion at line 61-64 (`orb = request.app.state.computation_config.orbs.natal`), rather than checking the stored chart's own `computation_config_content_hash` (which 2.3/2.7 both carefully stamp on every write for exactly this kind of traceability). If the natal orb in `data/computation.toml` changes between when a chart was stored and a later view (after a restart), the wheel silently renders a different aspect set than what is actually persisted on the `StoredNatalChart` row — with no warning to the operator, on the one route the epic exists to make trustworthy ("get a natal chart I can verify").

The remaining findings were reviewed for plausibility and source quality but not independently re-executed; each carries file:line evidence from the agent that found it:

- Superseded-chart chain (2.7) is tested through the chart-wheel and delete HTTP paths only at depth N=1 (one correction) — never exercised at N=2 (`tests/test_http_client_correction.py`, `tests/test_http_client_deletion.py`, `tests/test_http_chart_wheel.py`).
- A delete (2.8) racing a correction (2.7) for the same `client_id` can hit an unhandled `NoResultFound`/`IntegrityError` inside `correct_client_and_chart()` and surface a bare 500 rather than 404/409 (`shell/adapters/postgres/client.py:183-188`) — same class as the concurrency gap already deferred for 2.7's own "one current chart" invariant.
- `chart_wheel_view` reads `Client` and its current `StoredNatalChart` in two separate, unsynchronized statements (`shell/http/routes/chart.py:47-56`); a correction landing between them could pair stale Client birth data with the already-corrected chart.
- `create_client_with_chart()` and `correct_client_and_chart()` build an identical `StoredNatalChart(...)` construction block verbatim with no shared helper (`shell/adapters/postgres/client.py:140-150` vs `192-202`) — the same class of unguarded duplication 2.8 explicitly built a test to prevent for the cascade table list, but not here.
- No composite index on `natal_chart(client_id, superseded_at)` even though three separate stories (2.6, 2.7, 2.8) each independently added a hot-path query filtered on that pair.
- The delete-confirmation copy says "the superseded chart" (singular) regardless of how many corrections actually preceded the deletion.
- `create_client`/`correct_client`'s plain-text success responses carry no link to `GET /clients/{id}/chart` — the verification view 2.6 built for exactly this moment.
