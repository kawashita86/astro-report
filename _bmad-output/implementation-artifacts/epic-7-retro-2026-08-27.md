## Findings

### Aggregate view — spec-to-implementation reconciliation

**No divergence.** Every constraint in `epic-7-context.md` and every frozen story spec is built as
written:

- All Corpus data in Postgres, nothing on the container filesystem — only a `corpus_entry` table and
  the `_BACKUP_MODELS` export; no filesystem writes. Source: `shell/http/routes/corpus.py`,
  `migrations/versions/0019_corpus_entry.py`.
- Paired/unpaired marked at record time, `paired` a stored boolean not derived from the link — 
  `corpus_entry.py:70`, `corpus.py:224` (`is_paired = paired_field == "paired"`).
- A paired entry with the Client not in the app stays paired with `client_id`/`month` `NULL`; a
  Client is never invented — `corpus.py:244-256` validates a *non-empty* `client_id` against an
  existing row, else 422; an empty one is stored `NULL`. Test: `test_paired_entry_with_no_client_and_no_month_persists_with_nulls`.
- `corpus_entry` joins the FR-29 Client-deletion cascade — `_CLIENT_CASCADE_TABLES` gains
  `"corpus_entry"` (`client.py:58` in diff) and `delete_client_and_derived` gains the deletion loop
  in the first batch (`client.py:354` in diff); `client_id IS NULL` entries are untouched.
- Composition view always reachable, no batch job, no manual query — three ints derived in Python
  from the list `GET /corpus` already loads, zero extra queries (`corpus.py:135-138`).
- Corpus routes carry the same auth — nothing added to `shell.http.auth.ALLOWLIST`; anonymous
  `GET`/`POST` on every `/corpus*` path returns 401 (`test_anonymous_*` in `test_http_corpus.py`).
- Corpus entries in the logical backup export — `CorpusEntry` inserted into `_BACKUP_MODELS`
  immediately after `Client` (`backup.py:63` in diff); "ten tables" wording → "eleven"; `_TABLE_ORDER`
  in `test_http_backup.py` updated; both structural invariant tests
  (`test_backup_model_order_is_fk_safe`, `..._covers_exactly_the_client_cascade_tables...`) still hold.
- Ingest logs nothing — there are no logging/telemetry calls in `corpus.py` at all, so "no Corpus
  prose or client identifiers in logs" is satisfied by construction.

The deliberate sequencing decisions are honoured: `client_id` ships nullable in 7.1 (not 7.2) so the
cascade AC and the durable `test_every_table_with_a_client_id_foreign_key_is_covered_by_the_cascade_constant`

shows `0 total · 0 paired · 0 unpaired`.

### F1 — `_parse_form` urlencoded-body parser is now a third near-verbatim copy — low

`shell/http/routes/corpus.py:58-87` re-implements `_FormTooLarge`, `_FormNotUtf8` and `_parse_form`
byte-for-byte from `shell/http/routes/style_guide.py:56-83`, which itself mirrors
`shell/http/routes/clients.py:100-131`. Three route modules now carry the same hand-rolled
"read the raw body, cap at N bytes, decode UTF-8, `parse_qsl`" block, differing only in the
`_MAX_*_FORM_BODY_BYTES` constant. Story 7.1's Code Map explicitly directed this ("full template for
`corpus.py`"), so it is spec-sanctioned, not an implementer slip. Source: `corpus.py:58-87` vs
`style_guide.py:56-83` vs `clients.py:100-131`. Disposition: **accept as-is** for epic 7 (followed
instruction); the extraction is a cross-cutting cleanup. Process lesson: a shared `shell/http/form.py`
would stop the 4th copy — same class as still-open `epic-2-retro-item-13` / `epic-6-retro-item-51`.

### F2 — `_MONTH_PATTERN` regex duplicated across two route modules, with a misattributed provenance comment — low

`shell/http/routes/corpus.py:55` re-declares `_MONTH_PATTERN = re.compile(r"^\d{4}-(0[1-9]|1[0-2])$")`,
identical to `shell/http/routes/report_runs.py:69`. Story 7.2's Code Map instructed the re-declaration
("do not import the route module that also defines it"), so the duplication is deliberate. But the
comment at `corpus.py:51-54` attributes the pattern to `shell/runner/month.py` ("the same shape
`shell/runner/month.py` is contracted to accept") — `shell/runner/month.py:49` actually validates via
`datetime.strptime(month, "%Y-%m")`, which accepts unpadded months (`2026-5`) and is therefore
**looser** than this regex. The regex was in fact copied from `report_runs.py`. Source: `corpus.py:51-55`,
`report_runs.py:69`, `shell/runner/month.py:49`. Disposition: **fix now** (comment correction; the
regex itself is correct and stricter-is-safer). Process lesson: a single `YYYY-MM` regex constant in a
shared module would end this.

### F3 — FR-29 cascade tests for `corpus_entry` run without DB-level FK enforcement — low/medium

`tests/test_corpus_store.py:34` builds its engine with `create_engine("sqlite://")` — no
`PRAGMA foreign_keys=ON` listener, unlike the `test_http_corpus.py` route fixture which at least uses
`StaticPool` + `check_same_thread=False` (still no FK pragma, but route tests don't need it). The
behavioural cascade tests (`test_a_paired_corpus_entry_is_deleted_with_its_client`,
`test_an_unpaired_corpus_entry_survives_a_client_deletion`,
`test_deleting_one_client_touches_only_its_own_paired_entry`) are sound and *would* catch a removed or
wrong deletion loop, because they assert on row presence directly. What they cannot catch: the
`corpus_entry.client_id` FK is declared `sa.ForeignKey("client.id")` with **no `ON DELETE` clause**,
so on real Postgres an incomplete cascade loop raises `ForeignKeyViolation` — a failure mode no test
exercises, because SQLite FK enforcement is off. This is exactly the gap
`epic-6-retro-item-52` named ("PRAGMA foreign_keys=ON for every `delete_client_and_derived` test, not
just the one Story 6.4 regression"); epic 7 added a new cascade-test file that repeats the weaker
pattern. Source: `tests/test_corpus_store.py:34`, `migrations/versions/0019_corpus_entry.py:24-33`,
cross-ref `epic-6-retro-item-52`. Disposition: **fix now**, folded into item 52.

### F4 — migrations 0019 + 0020 have never run against a real Postgres — medium (carry-forward)

Per still-open `epic-6-retro-item-46`, `alembic upgrade head` on a stock Postgres fails at revision
`0014_bound_client_and_chart_string_columns` (42 chars) because the default
`alembic_version.version_num` column is `VARCHAR(32)`. Every revision after `0014` — now including
epic 7's `0019_corpus_entry` and `0020_corpus_entry_pairing` — is unreachable online behind that
block. `tests/test_migration_chain.py` only ever runs `alembic upgrade head --sql` (offline SQL
generation, `test_an_offline_upgrade_runs_env_py_and_emits_the_chain` at line ~130), which never
creates or writes `alembic_version` and so cannot see the ceiling. Story 7.1's own Verification block
(`uv run alembic upgrade head --sql`) has the identical blind spot. Epic 7 did the right thing on its
own migrations — the new revision ids are 17 and 25 chars, well under 32 — so it added **no new
instance** of the bug, but its schema changes inherit the unverified-on-target-DB risk and push the
unverified online-migration span two revisions longer. Source: `epic-6-retro-item-46`;
`tests/test_migration_chain.py:104-131`; revision-id lengths (`0019_corpus_entry` 17,
`0020_corpus_entry_pairing` 25, `0014_bound_client_and_chart_string_columns` 42). Disposition:
**defer** to item 46; reinforces its urgency before epic 8.
