## Findings

### Aggregate view — architecture delta

Confined to the declared surface and then some. `core/` is verifiably untouched. The serving
application is untouched except for the `GEMINI_DATA_TERMS_VERIFIED_AT` date literal. The one new
module, `shell/restore.py`, is an operator CLI that `shell/http/` never imports — spec 8.5 is
explicit that restore is "an operator CLI plus a written runbook, not an authenticated endpoint",
and `git grep` confirms no route or middleware references it. No new import cycles; `restore.py`
imports `_BACKUP_MODELS` live from `shell/http/routes/backup.py` (the single source of truth for the
table set and its FK-safe order) rather than re-listing it. No god-class growth — the largest
absolute file the epic touches in `shell/` is `restore.py` itself at ~300 LOC. The bulk of the
+4,900-line diff is four new standalone test files and four new Markdown records.

### F3 — NFR-5 says "any bounded regeneration included"; the composed p90 excludes it — accepted deviation, recorded

`report_p90_seconds = 119` is the **single-generation-call** figure (1 s local + 118 s p90 of a
live `gemini-2.5-flash` n=10 sample). NFR-5's own text counts "any bounded regeneration" toward the
3 minutes, and the live sample found **8/10** drafts passed citation validation on the first try —
so a real Report has a ~20% chance of a second ~100 s generation call, landing at ~220–250 s, over
the 180 s budget. `latency.md`'s "Known limitation" section records this; Francesco's 2026-08-27
decision was to record it and re-measure against real post-launch traffic rather than revise the
budget. The epic context explicitly carves this out ("A run needing citation- or Gate-driven
regeneration may exceed it; that case is a recorded known limitation, not a blocker"). Source:
`docs/release-validation/latency.md:44-73,199-202`; `epic-8-context.md:20`. Disposition:
**accept as-is** — recorded here so a later retro does not re-flag it as a fresh gap. Upstream
lesson: the re-measure against `ExportRecord.elapsed_seconds` once traffic exists is the real
close-out (tracked in the record's Re-measure trigger).

### F4 — the storage projection rests on one non-adversarial fixture and a JSON-length proxy — low, defer

`payload_p90_bytes` ≈ 63 KiB comes from `len(canonical_json_bytes(row.payload))` (not bytes-on-disk)
over 12 consecutive months of the single Fort Worth, TX fixture on an in-memory SQLite stand-in.
Payload size scales with transit-event count, and Story 8.1's adversarial fixtures
(retrograde-station month, double-lunation month) are designed to maximise event counts, so a
defensible upper p90 would be higher. The record discloses this and leans on the 1.5× overhead
factor plus the 50%-ceiling policy trigger to absorb the gap. Source: `deferred-work.md` story 8.4
entry; `spec-8-4-*.md` Design Notes ("Why project on the Payload alone", "GB vs GiB"). Disposition:
**defer** — re-measure against the adversarial set (and ideally a second birth chart) at the next
`checked` bump, or add an explicit accepted-deviation note that the typical-month sample + 1.5×
factor is the deliberate basis. Not release-blocking: the policy fires at 50%, well before any
plausible under-estimate matters.

### F5 — `restore-rehearsal.md` records `outcome = "pass"` while the real-Postgres rehearsal is explicitly pending — medium (open item)

Story 8.5's title is "Restore from a backup, **for real**" and the epic context requires "a
restore-from-export **actually rehearsed**". The delivered record's `## Still outstanding` section
says plainly: "What has **not** yet happened is the operator running `python -m shell.restore`
against a freshly provisioned empty Neon branch and signing off on the result." Yet `outcome = "pass"`
and the guard suite is green, because the guard cannot distinguish "rehearsed for real and ratified"
from "proven in-process, real step pending, outcome set to pass anyway". For a release-gate epic
whose whole purpose is rehearsal-before-release, the green suite over-signals readiness. Source:
`docs/release-validation/restore-rehearsal.md:13-22,142-160`. Disposition: **fix now** — run the
real rehearsal (action item 1). Per Francesco's accepted-with-open-items verdict this is a tracked
open item, not a retro blocker; it is, on the epic's own framing, a **release** blocker. Upstream
lesson: a guard that asserts `outcome == "pass"` needs a companion field it cannot satisfy from
in-process evidence alone (e.g. a `rehearsed_against` enum that must read `real-postgres`) so
"pass on a placeholder" is structurally impossible.

### F6 — the Story 8.5 restore runbook depends on the still-open `epic-6-retro-item-46` and fails as written — medium/high (open item)

`restore-rehearsal.md`'s runbook step 3 is `uv run --env-file .env alembic upgrade head` against a
fresh empty Neon branch. Per still-open `epic-6-retro-item-46`, `alembic upgrade head` on a stock
Postgres fails at revision `0014_bound_client_and_chart_string_columns` — the revision id is **42
characters** (confirmed: longest in `migrations/versions/`, next is 30) and the default
`alembic_version.version_num` column is `VARCHAR(32)`. So the disaster-recovery procedure this epic
ships **cannot currently be executed end to end on a real Postgres** — it breaks at the
schema-apply step, before restore runs at all. This is also the concrete reason F5's dry-run is
still pending and cannot simply be rubber-stamped: running it would surface this failure. Source:
`docs/release-validation/restore-rehearsal.md:80`; `epic-6-retro-item-46` (sprint-status
`action_items`); revision-id length 42 vs `VARCHAR(32)`. Disposition: **fix now**, folded into
action item 2 — item 46 is no longer just a migration-hygiene item, it gates the epic-8 restore
rehearsal. `epic-7-retro-item-55` (which asked to re-prioritise item 46 as gating epic 8) was not
acted on; its substance rolls into action item 2.

### F7 — the opt-in measurement harnesses are skipped every CI run and can rot silently — low, defer

`test_measure_latency` (8.3) and `test_measure_payload_size` (8.4) are `@pytest.mark.skipif` unless
`RUN_LATENCY_MEASUREMENT` / `RUN_STORAGE_MEASUREMENT` is set, and both import many private symbols
from `tests/test_runner_driver.py` (`_create_client_and_chart`, `_drive`, `_FakeGenerator`,
`_a_generated_draft`, the module `_COMPUTATION_CONFIG` / `_SECTIONS_CONFIG` / `_VOCABULARY` /
`_EPHEMERIS_IDENTITY`). Nothing periodically exercises them, so a `test_runner_driver.py` refactor
breaks the harness while the always-on record-guards stay green — the release gate can then pass on
a record no one can regenerate. Source: `deferred-work.md` story 8.4 entry (Blind Hunter). The
epic's 2 skipped tests in `pytest -q` are exactly these two. Disposition: **defer** — a scheduled
non-blocking job, or a lightweight always-on smoke that drives one run (not the full sample).

### F8 — release-validation records have no staleness enforcement — low, defer

All four records carry `checked = 2026-08-27`. Nothing fails when a `checked` date ages past a
reasonable horizon, the long "Re-measure trigger" lists are prose only, and no guard binds a
record's quoted NFR/terms text to `epics.md` / the PRD beyond the single budget number. The runtime
future-date guard on `GEMINI_DATA_TERMS_VERIFIED_AT` is the still-open `epic-4-retro-item-25`; a
"record too old" signal has no owner at all. Source: `deferred-work.md` story 8.3 entry. Disposition:
**defer** — a shared max-age assertion in the F1 helper (`checked >= today - N months` → fail),
plus a decision on `epic-4-retro-item-25`.

### F9 — ratified release-gate decisions live only as prose, same-day / same-person, no decision index — low, defer

The 8.2 (data-terms benign-change assessment), 8.3 (record-the-regeneration-risk-don't-revise-budget)
and 8.4 (storage-growth policy) decisions are each ratified `Francesco` / `2026-08-27` inside their
own release-validation file, with no linked commit, PR or review reference and no
`docs/decisions/` index pointing at them. "Raised as an explicit decision rather than absorbed"
(Story 8.4 AC-3) is satisfied in-file but not discoverable. Source: `deferred-work.md` story 8.4
entry. Disposition: **defer** — a lightweight `docs/decisions/` log or a release-checklist entry
format the records link back to.

### F10 — `canonical_json_bytes` / `ReportPayload` docstrings claim canonical JSON the write path does not produce — trivial, defer

`core/payload/freeze.py::canonical_json_bytes` and `shell/adapters/postgres/report_payload.py`'s
class docstring both assert every persisted `ReportPayload` "is written as" canonical JSON (sorted
keys, no insignificant whitespace), but the write path hands the plain dict to SQLAlchemy's `JSON`
column, which serializes with the engine default `json.dumps` (`", "` / `": "` separators,
insertion-order keys) — `shell/http/app.py` builds the engine with no `json_serializer`. Pre-existing
inconsistency, surfaced because Story 8.4's size measurement had to pick one serialization. Low
functional impact: the column is Postgres `json` not `jsonb`, and payload ids are hashed from
`canonical_json_bytes` separately. Source: `deferred-work.md` story 8.4 entry (Blind Hunter).
Disposition: **defer** — correct the docstrings, or install a canonical `json_serializer` on the
engine.

### F11 — a prior-retro lesson landed proactively in new code — positive, no action

`tests/test_restore.py` enables `PRAGMA foreign_keys=ON` on its restore-target engine so the
`_BACKUP_MODELS` FK-safe insert order is genuinely exercised — exactly the enforcement
`epic-6-retro-item-52` / `epic-7-retro-item-54` asked for, applied to a brand-new test file without
being told to by an open item. Worth recording: the "new cascade/FK tests must use real FK
enforcement" lesson is now being pattern-matched into new work. Source: `spec-8-5-*.md` Boundaries
("enable `PRAGMA foreign_keys=ON` on the restore target"); `tests/test_restore.py`.
