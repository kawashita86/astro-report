### Diff-scope review (bmad-review: adversarial, edge-case-hunter, verification-gap)

**adversarial** (re-verified against the actual source, not taken on the subagent's word):

1. **A two-write stage function's partial flush, retried by `with_backoff`, can poison the transaction and defeat the terminal-failure mechanism itself.** Verified end to end: `store_report_payload`/`store_report_theme` each only `session.flush()`, never commit (confirmed by their own tests, `tests/test_report_payload_store.py::test_store_report_payload_only_flushes_never_commits` and `tests/test_report_theme_store.py::test_store_report_theme_only_flushes_never_commits`) — so `_run_payload_ready` (`shell/runner/driver.py:336-381`) leaves an uncommitted-but-flushed `ReportPayload` row in the session if `store_report_theme`'s later flush raises. `with_backoff` (`shell/runner/backoff.py:56-67`) retries by calling the *same* stage function again on the *same* session with no rollback between attempts. The retry's second call to `store_report_payload` re-inserts against `ReportPayload.report_run_id`'s unique constraint, raising `IntegrityError` — and in Postgres that aborts the transaction. `drive()`'s except-block (`shell/runner/driver.py:563-582`) then tries `session.add(run); session.commit()` to record `stage_failure_count`/`failed_at` — against an already-aborted transaction, which itself raises, uncaught anywhere in `drive()`. **Consequence**: the one stage most likely to hit this (payload_ready, immediately upstream of the rate-limited draft_ready) can, on a legitimate transient failure in its second write, produce an unhandled 500 that never records the failure on the `ReportRun` row — silently defeating Story 4.8's whole terminal-failure guarantee for exactly the case it exists to catch. **Route**: fix now — `with_backoff` or each two-write stage function needs a `session.rollback()` between attempts (or the stage needs to be genuinely idempotent, e.g. delete-then-insert or upsert).
2. **`RecordedResponseGenerator` transitively imports `google.genai` at import time, contradicting its own "never touches network/filesystem/google.genai" intent — and the test meant to guarantee this doesn't check for it.** Verified: `shell/adapters/local/generator.py:25-31` imports `_DATE_TOKEN_SECTIONS`/`_SECTION_FIELD_NAMES`/`_collect_known_entry_ids`/`_validate_citations`/`_validate_no_date_tokens` directly from `shell/adapters/gemini/generator.py`, whose module body (line 23) does `from google import genai`. Importing the "local-only" adapter therefore always imports `google-genai` too — it lands in `sys.modules` regardless. `tests/test_recorded_generator.py::test_never_imports_google_genai` only checks `"genai" not in vars(module)` / `not hasattr(module, "genai")` on `shell/adapters/local/generator.py`'s own namespace, which stays true even though the transitive import happened — the test gives false confidence about the exact boundary it names. **Consequence, corrected**: the subagent's stated consequence ("a minimal environment without `google-genai` installed can't import `RecordedResponseGenerator`") does **not** currently manifest — `pyproject.toml:11` lists `google-genai==2.19.0` as an unconditional top-level dependency, always installed regardless of environment, so nothing breaks today. The real, live problem is narrower but still genuine: Story 4.9's own stated intent ("never imports `google.genai`... never touches the network, a model or the filesystem") is factually false as built, and `test_never_imports_google_genai` gives false confidence about exactly that boundary — a future change to `shell/adapters/gemini/generator.py` (e.g. a module-level side effect added there) would silently run whenever `RecordedResponseGenerator` is imported, undetected by this test. **Route**: fix now, but as a correctness-of-intent / test-honesty item, not an active production bug — extract the shared validation helpers (`_collect_known_entry_ids`, `_validate_citations`, `_validate_no_date_tokens`, the two constants) into a provider-neutral module neither adapter's private namespace, so the boundary the story and the test both claim is actually true.
3. **`GEMINI_DATA_TERMS_VERIFIED_AT` is validated as parseable but never as sane.** Verified: `shell/config.py::_read_gemini_data_terms_verified_at` (lines 280-303) only calls `date.fromisoformat(raw)` — no check that the date isn't in the future, and nothing elsewhere re-checks or expires it after startup. **Consequence**: NFR-17's "verified, and the check recorded" guarantee is satisfied forever by one value; a typo like `2126-01-15` passes silently, and a genuinely stale multi-year-old verification is indistinguishable from a fresh one. **Route**: fix now, but low cost — reject a future-dated value at minimum; a staleness warning (not a hard failure) is a reasonable stretch addition, not required for this epic's scope.
4. **`GeminiGenerator.generate()`'s prompt-construction step falls outside the try/except that produces typed `GenerationError`s.** Plausible per the module's own docstring stating every failure mode should surface as a typed `GenerationError` "rather than letting a raw SDK or JSON exception escape untyped" (`shell/adapters/gemini/generator.py:1-14`) — not independently re-read line-by-line against the try block's exact boundaries. **Route**: defer — worth a follow-up check of the exact try/except span before treating as confirmed.
5. **`_entry_date()` (`shell/http/draft_view.py:105`) raises a bare `ValueError` on an unrecognized/missing day-list `"kind"`, uncaught up through `view_report_draft()`.** Not independently re-verified against the full call chain's exception handling (e.g. whether FastAPI's own exception middleware already turns this into an acceptable 500 vs. crashing the process) — plausible on its face given `_entry_date`'s signature returns `str` unconditionally with no error path shown in the finding. **Route**: defer — low likelihood (requires a new/malformed event kind, which nothing in this epic introduces) but cheap to guard; worth a follow-up look before committing engineering time.
6. **`derive_theme()`'s dominant-aspect sort has an undocumented tiebreak-by-encounter-order** (`core/memory/derive.py::_aspect_tightness_key`) for two aspects perfecting at the exact same instant — unlike the same-identity-duplicate case in `core/memory/diff.py`, which the epic's own session logs record as an explicitly accepted, documented limitation (see Process lessons above). **Route**: defer — real but narrow (exact-timestamp ties), and a one-line fix (add a lexicographic tiebreak) whenever someone is next in this file.
7. **The uniform `except Exception` in `with_backoff`/`drive()` treats a deterministic failure (a citation-validation `GenerationError`, a `StyleGuideMissingError`) identically to a transient one (a rate limit), spending up to 5 `drive()` calls (~15 Gemini attempts) before surfacing a failure that retrying could never fix.** This is a deliberate, documented design choice (`shell/runner/backoff.py:1-9`: "nothing here knows what it is retrying... AD-10 rules against two builders inventing incompatible retry semantics"), not a defect that slipped through unnoticed — **route: accept as a known design tradeoff**, not fix-now, but worth naming as a candidate improvement (retry only step-classified-transient `GenerationError`s) if Gemini quota waste becomes a real operational cost.
8. **`RecordedResponseGenerator` cites the entire day-list in one `Sentence` per Section 6/7, rather than one `Sentence` per entry** — every day in local dev renders the identical placeholder caption, so a real per-entry-caption rendering bug in Story 4.6 could never be caught by exercising the local environment, only by a real Gemini response. **Route**: defer — a local-dev-fidelity nice-to-have, not a production defect (the adapter's own docstring already frames it as a "generic placeholder," not a rendering-fidelity tool).
9. **`StageFn`'s signature grew a 7th positional parameter (`generator`) in Story 4.6 that 3 of 4 registered stage functions ignore, with nothing enforcing the registry's positional call site against each function's actual signature until `with_backoff` raises at runtime.** A real but low-probability code-quality point (a future stage-registration mistake surfaces as a generic "stage failed" event via the same broad except-block, rather than a clear signature error) — **route: accept as-is**; the existing design already documents the tradeoff (a single uniform `{name: function}` registry over per-stage plumbing) and the risk only materializes when Story 3.9+ adds a new stage.
10. **`deserialize_generated_draft()` does unconditional field lookups against an immutable, append-only `ReportDraft.draft` JSON blob with no stored schema version** — a future field rename/removal on `GeneratedDraft` would make every already-persisted draft permanently unreadable (`KeyError`) since rows can never be updated. **Route**: defer as a process lesson for whoever next changes `GeneratedDraft`'s shape (add a `draft_schema_version` column then, matching `style_guide_version`/`sections_config_version`'s existing pattern) rather than a fix-now for this epic — no such change has happened yet, so there's nothing broken today.

**edge-case-hunter** (each re-checked against the actual source, not taken on the subagent's word):

1. **Concurrent `drive()` calls on the same stage can spuriously increment `stage_failure_count`.** Verified: `ReportPayload.report_run_id` carries `unique=True` (`shell/adapters/postgres/report_payload.py:50`, deliberate — "PRD FR-14's every stored Report has exactly one stored Report Payload"), so two concurrent `drive()` calls racing the same not-yet-advanced stage (e.g. two browser tabs, or a double-click on start/poll) will have the losing transaction's insert raise `IntegrityError`. `drive()`'s `except Exception` block (`shell/runner/driver.py:563-582`) has no special case for this — it counts the loser's `IntegrityError` as a genuine stage failure and increments `run.stage_failure_count`, even though the stage itself succeeded via the winning transaction. Self-healing in the common case (the next `drive()` call sees `run.stage` already advanced and skips it), but five such races in a row would trigger a false terminal failure. **Route**: fix now — catch `IntegrityError` (or the specific unique-violation) in that block and treat it as "another request completed this stage," not a failure.
2. **`_DATE_TOKEN_PATTERN` (`shell/adapters/gemini/generator.py:70-75`) is a best-effort heuristic, explicitly documented as such** ("not a completeness guarantee... deliberately does not attempt spelled-out ordinals"). Verified two real gaps against the actual regex: (a) false positive — a non-date numeric range like `"3-4"` in giorni_favorevoli/di_attenzione would match `\b\d{1,2}[/-]\d{1,2}\b` and wrongly raise `GenerationError`, over-rejecting safe content; (b) false negative — a dot-separated date (`"15.01"`) or abbreviated month (`"15 gen"`) would not match, letting a real date-shaped token slip through the one place the epic's requirements explicitly forbid it. **Route**: (a) accept as-is — fails safe (over-rejection, not a silent violation), and already documented as a known heuristic limit. (b) fix now — the false-negative direction is a silent-grounding-safety gap on a hard requirement ("dates are code-projected upstream... the model must never emit a date token" per `epic-4-context.md`), worth tightening even within a heuristic.
3. **`most_recent_prior_report_theme` (`shell/adapters/postgres/report_theme.py:102-124`) has no tiebreak for same-month `ReportRun`s.** Verified: `ReportRun` (`shell/adapters/postgres/report_run.py:56-118`) carries no unique constraint on `(client_id, month)`, so nothing in the schema prevents two `ReportRun` rows for the same Client and month (e.g. a user re-triggering generation for a month whose prior run stalled or was superseded by a client correction). The query orders only by `ReportRun.month.desc()` with `.limit(1)` and no secondary key, so a tie between two same-month runs' themes resolves non-deterministically. **Route**: fix now — add `StoredReportTheme.created_at.desc()` (or `ReportRun.created_at.desc()`) as a tiebreak.
4. **`RecordedResponseGenerator._section_subtree` (`shell/adapters/local/generator.py:46-56`) would raise `AttributeError` if `payload["day_lists"]` or `payload["sections"]` were present but `None`** (`.get("day_lists", {})` only substitutes the default when the key is *absent*, not when its value is `None`) rather than degrading to an empty subtree. Not independently confirmed that real `freeze_payload()` output ever stores `None` there — likely low probability given payload assembly always constructs dicts — and is really the same root issue as verification-gap finding #1 above (the adapter is never exercised against a real frozen payload). **Route**: fold into that same action item rather than tracking separately — a test against real `freeze_payload()` output would settle whether this path is reachable at all.

**verification-gap:**

1. **`RecordedResponseGenerator` is only tested against hand-built payload fixtures, never a real `freeze_payload()` output.** `tests/test_recorded_generator.py`'s `_multi_section_payload()`/`_empty_payload()` fixtures are hand-constructed and include a `"profile": {"id": "profile-amore-1"}` field the real pipeline never produces — `core/types/domains.py`'s profile dataclasses (`AmoreProfile`/`DomainPlanet`/`DomainHouse`) carry no `id` field, and `core/payload/freeze.py::_freeze_section` only assigns ids to event tuples, never to `profile`. No test feeds the adapter a payload actually produced by `freeze_payload()`, unlike `tests/test_gemini_generator.py`'s `test_citation_validation_finds_ids_in_a_real_freeze_payload_shaped_payload`, which has no counterpart for the recorded adapter. **Consumer**: `shell/runner/driver.py::_run_draft_ready` feeds `RecordedResponseGenerator` exactly `stored_payload.payload` (`freeze_payload()`'s own output, unmodified per `shell/adapters/postgres/report_payload.py:104`) whenever `get_generator()` selects it under `Environment.LOCAL`. **Consequence**: a divergence between the fixture shape and the real frozen-payload shape (e.g. `_section_subtree`'s id-walking logic assuming ids where none exist) would surface as silently-empty citations or a crash under `docker compose up`, and no existing test would catch it, since every fixture matches the code's current assumptions rather than the real contract.
2. **The adapter's "never touches network/filesystem" guarantee is checked only at import time, not at runtime.** `tests/test_recorded_generator.py::test_never_imports_google_genai` (lines 216-221) only asserts `"genai" not in vars(module)` / `not hasattr(module, "genai")` — it inspects the module's top-level namespace, not actual I/O during `generate()`. No socket-blocking or filesystem-blocking test exists (`tests/conftest.py`/`pyproject.toml` carry no `pytest-socket` or equivalent). **Consequence**: a future change adding a local `import google.genai` inside the method body (rather than at module scope), or any network/filesystem call through a different library, would pass this test while breaking the exact guarantee `compose.yaml`'s comments and the story's own intent rely on — that local dev never spends real Gemini quota.
