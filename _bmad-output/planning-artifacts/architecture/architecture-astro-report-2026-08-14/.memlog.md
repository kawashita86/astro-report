- (decision) GROUNDEDNESS GATE (Francesco's choice): three independent layers. (1) REMOVE - Sections 6 and 7 day-lists are rendered from the Report Payload by pure code; the Generator never types a date into a day-list, so PRD Assumption 1's misfiled-day error class becomes structurally impossible rather than merely detectable. (2) CITE - narrative Sections are returned as structure, each sentence carrying the Payload entry ids it rests on; an astronomically-loaded sentence citing nothing is a violation. (3) VERIFY - a pure core function extracts Claims by closed Italian astronomical vocabulary and requires each to agree with the entries it cites. Prevents: a single-mechanism Gate whose false-negative rate is unknowable (PRD s.12, SM-7). Rejected: extraction-only (leakage hides in paraphrase), citations-only (a correct citation can carry a wrong date), second-model-as-judge (polices a non-deterministic writer with a non-deterministic checker, contradicting the product principle).
- (decision) PRD OPEN QUESTION 1 ANSWERED architecturally: the Claim / interpretation boundary is a deterministic classification, not a judgement. A sentence is a Claim iff it contains a token from the CLOSED Italian astronomical vocabulary - ten planets, twelve signs, 'casa' + ordinal, day-of-month numerals, retrogrado/stazionario. A sentence containing none asserts nothing checkable and is governed by the Style Guide, not the Gate. Known and accepted hole: a sentence that leans on a fact without naming it ('Il mese ti chiede pazienza' after a Saturn passage) is not policed, because it is not verifiable against a Payload by any mechanism. - (decision) EXECUTION SHAPE (Francesco's choice): a report run is a checkpointed ReportRun row in Postgres advancing through persisted stages (natal_ready -> transits_ready -> payload_ready -> draft_ready -> gate_passed -> exported). Every stage output is persisted before the next begins. Prevents: losing an in-flight run to Render's spin-down, a redeploy or a Gemini rate-limit stall, and recomputing stages that already succeeded. Retry is free because the core is pure. Gives UJ-1's forty-report batch a natural drain against the 10 RPM ceiling with no queue infrastructure. Rejected: synchronous request/response (a stall loses the whole run), in-process background task (run state lives only in memory, lost silently on restart).
- (decision) PRD OPEN QUESTION 2 ANSWERED (Francesco's choice): the ReportTheme is a PURE function of the Report Payload - dominant slow-planet aspects ordered by tightness, lunation houses, standing retrogrades - with no model involvement. Month-over-month continuity is therefore deterministic and cannot drift across a recurring client's year, and FR-18's 'nothing significant has changed' becomes a COMPUTED fact rather than a judgement the Generator makes. - (decision) AD-20 (new) ReportRun driver = hybrid non-blocking. Binds: FR-8-FR-22, FR-25, NFR throughput/latency, UJ-1; relates AD-9 (backoff, no failover) and AD-10 (checkpointed stages). Prevents: (a) a read (the poll GET) blocking on whole-run completion, which refreezes the operator's stage view and re-introduces 'a stall loses the request'; (b) the start POST blocking synchronously on generation, as it does today by calling drive() inline; (c) a later builder adding a queue/worker/cron to 'fix' latency, breaking the EUR0 + no-infra constraint the spine set; (d) two compliant units siting the advance mechanism differently (poll vs in-process task vs cron) and disagreeing on how an abandoned run resumes.
- (decision) AD-20 Rule: (1) A ReportRun is advanced only by the runner's single-stage advance function, invoked ONLY from the poll GET handler (GET /report-runs/{id}). Never from a background thread, asyncio task, queue consumer or scheduled job; adding one is a spine amendment. (2) At most ONE stage transition per request; that one stage's own duration -- including its single external call and AD-9 bounded backoff -- may extend that request; the response never chains into a second stage. (3) No handler's HTTP response waits on run completion. The start POST (POST /clients/{id}/report-runs) creates the row and returns immediately without advancing; the first stage runs on the first poll. (4) Single-flight per run: the advance acquires pg_try_advisory_xact_lock on the run id; if it cannot, another request holds it, so this request reads and returns the current stage without advancing. The lock releases at transaction end (commit, rollback, or connection loss on spin-down). (5) The advance is idempotent and re-entrant on its persisted input (AD-10); the cross-call counters (stage_failure_count/_MAX_STAGE_FAILURES, regeneration_count/_MAX_REGENERATIONS) are unchanged. (6) A run whose owning tab is closed pauses at its last checkpoint and resumes on the next poll GET of that run. There is no other resumption path, by design -- no scheduled or self-issued request advances a run; forward progress is bounded by genuine operator polling.
- (decision) AD-10 Rule amended in place (one clause added, no renumber): after 'Re-driving a run resumes at the first incomplete stage' add a pointer -- 'AD-20 governs what invokes that advance and when (the poll GET, one stage per request, never a background job)'.
